# How to 用 DropIt 完成一次有代码证据的 AI 应用面试讲解

目标：面试官追问时，你能从“我用了某框架”走到“输入是什么、状态怎么变、失败怎么处理、证据在哪、还有什么没实现”。不是背一篇包装稿。先完成[运行教程](tutorial-run-and-observe.md)，理解[架构解释](explanation-agent-architecture.md)，字段查[技术参考](reference-api-tools-and-data.md)。返回[学习首页](README.md)。

## 1. 准备材料，不临场依赖模型运气

在自己的演示项目准备可用曲库，并事先验证一个搜索、一个相似查询、一个可行 Set 和一个冲突 Set。保存去除 Key、个人路径等敏感信息的结果截图，记录源代码 commit 和运行环境；演示前跑轻量测试和构建。

准备打开五个位置：agent.py 的 stream_chat、graph.py 的 build_graph/extract_command、retrieval.py 的 search/_rank、set_planning.py 的 validate_and_repair_set，以及恢复测试。不要先展示整个数据库文件，也不要现场导入上百首歌曲等待云端处理。

如果没有真实模型验收，就用测试解释确定性链路，并明确说明尚未验收云端。测试通过与真实模型可用是两件事，不要让面试演示冒充不存在的结果。

## 2. 90 秒项目介绍

可以用下面的结构，再替换成自己确实做过的工作和数据：

> 我做的是一个面向本地曲库的 DJ 助手，提供曲库搜索、相似歌曲推荐和 Set 编排。音频在本地用 librosa 提取节奏、调性和能量等特征，再通过描述模型和文本 embedding 建立歌曲描述索引；事实和运行状态放 SQLite，向量放 Chroma。
>
> 在线部分使用一个受控 LangGraph。先由规则、可选意图模型确定分支，聊天模型提取该分支的结构化参数，代码负责检索、规划、校验和持久化，最后模型依据证据解释结果。它不是自由 ReAct 或多 Agent 系统。
>
> 我重点处理了 Set 无效结果不能保存，以及重复请求、进程中断后的恢复：有限修复、持久 checkpoint、租约 fencing 和幂等写入。当前是单机学习项目，没有用户鉴权、自动混音和大规模检索；质量指标也会按数据集和版本说明边界。

若某部分并非你参与设计，表述为“项目实现了，我阅读/验证了”，不要据为个人成果。模型供应商名称不是亮点，职责划分与验证方法才是。

## 3. 五分钟演示顺序

1. **30 秒：可运行。** 展示 health 和曲库实际状态，说明 analyzed 不等于向量 ready。
2. **60 秒：搜索证据。** 做一次带过滤的搜索，在 retrieval.py 指出先范围过滤、后语义排序；说明描述不是多模态音频向量。
3. **60 秒：受控执行。** 在 build_graph 找搜索、相似和 Set 分支，说明三个业务能力与十一种步骤节点的区别。
4. **90 秒：成功与失败。** 展示可行 Set、validator 的结构化 issues 和不可行 Set；失败不保存、最多两轮，不是“多模型商量到满意”。
5. **60 秒：工程可靠性。** 展示同 run_id 复用或相关测试，说明 checkpoint、幂等、租约各解决什么，以及外部调用可能重跑的限制。

结束时给出一个真实权衡：小曲库先用可解释全量余弦排序，后续若数据和延迟要求变化，再评估 ANN；不是“用了 Chroma 就已经具备百万级检索”。

## 4. 常见追问：回答、代码、证据和边界

### “这究竟是 Agent，还是 if/else 套壳？”

这是有限任务的 AI 工作流/受控 Agent 应用：模型理解语言并参与决策输入，程序维护步骤、状态和副作用；当前不是自主规划任意工具序列。LangGraph 的价值是显式状态和控制流、流事件和测试接口，不是自动让规则变聪明。三条简单链也可以用普通函数实现，选择图是为了让校验回路、恢复入口和进度更清晰。

看 graph.py 的 build_graph，测试 `test_agent_executes_controlled_graph_without_free_tool_loop`。被追问“为什么不直接函数调用”时承认可以，比较新增状态/回路后的维护成本，不用框架名充当答案。

### “为什么没 @tool，没有更多子图？”

当前节点直接 add_node 注册，参数来自 State/Runtime；@tool 解决的是模型工具调用 schema，不是普通图节点所必需。三个业务能力不足以要求三个子图，Set 的多个节点只是不同阶段。参考歌提取与匹配也分清：Graph 编排、Registry 匹配，不是复制两份匹配算法。

看 graph.py 的 extract_and_resolve_reference 和 retrieval.py 的 resolve_reference；测试参考歌缺失、重名和明确 ID。若未来切为自主工具选择，应重新设计权限与终止机制，而非简单加装饰器。

### “LLM 在哪里用？关掉还能工作吗？”

默认聊天模型用于路由专属参数提取、证据回答和需要时的历史摘要；曲库准备还用描述模型、文本 embedding；规则未命中可选 Ollama 分类。硬路由命中的请求不让主聊天模型自由挑工具。没有 Key 可以管理资源、运行纯业务测试；聊天入口统一 503，语义索引/查询也各需要对应模型。

看 agent.py 的模型工厂、graph.py 的 extract_command、main.py 的 create_app，区分“直接业务函数可运行”和“产品聊天接口可离线运行”。

### “RAG 为什么不是关键词查询？向量在哪里？”

音乐描述是检索文档，非空 query 在同一向量空间找相似内容，再提供事实给回答模型；精确 BPM/作者等先做结构化过滤。SQLite 存事实和索引状态，Chroma 存向量；当前读取候选向量后用 NumPy 排序，不调用 ANN query。空 query 是元数据查询，不能把每次搜索都叫向量 RAG。

看 retrieval.py 的 search/_rank、sqlite.py 的 music_vectors、chroma.py。测试范围、维度不匹配、缺索引、移除项目关联。以后扩大数据量，要评估过滤召回、ANN、延迟和更新一致性，不能直接假定数据库品牌解决这些问题。

### “模型能真正判断曲风、听懂音乐吗？”

当前从测量特征生成描述，不上传波形给多模态模型；能表达数值及有限听感关联，但不能保证知道乐器、流派、完整结构或现场可接性。相似推荐是描述余弦 0.8 加 BPM/调性/能量规则 0.2，非训练推荐器、非概率置信度。

看 librosa_analyzer.py 与 text_models.py，测试适配器只传测量事实。改进要先建真实 query→相关歌曲标注和听感评价，再决定是否引入音频 embedding；不要先声称“模型听懂音乐”。

### “生成的 Set 为什么可靠？修复是不是 Reflection？”

可靠性是可检查的硬约束：归属、重复、BPM、相邻变化、Camelot、时长、能量和必选曲目。有限确定性修复后再次校验，冲突不持久化。它是校验驱动循环，不是 LLM 自我反思或保证找到全局最优解；原曲长度相加也不同于实际混音时长。

看 SetValidator、SetRepairer 和图 validate_set/persist_set；测试 `test_constraint_conflict_sse_has_no_playlist_and_two_versioned_repairs`。还要承认手动调序/approve 没做完整硬约束复核。

### “服务在写完歌单后挂了，会重复吗？多个请求同时来呢？”

同 run_id 复用已完成步骤；消息和 Agent 歌单有数据库唯一约束，稳定歌单 ID 由项目和 run 派生。租约让一个执行者持有写权限，递增 fencing token 与有效期检查拒绝过期写入。租约本身不等于结果幂等，checkpoint 本身也不能阻止两个执行者争写。

看 checkpoints.py、sqlite.py 的 claim/write 检查和迁移 009/010；测试 `test_same_run_concurrency_persists_one_deterministic_playlist`、`test_claim_fencing_uses_two_connections_and_allows_expired_takeover`。不承诺外部 API exactly-once，崩溃窗口可能重复调用/计费；前端还未接 run_id 重试。

### “为什么不用 LangGraph 内置 checkpointer、Redis 或消息队列？”

目前用了自定义 SQLite 步骤快照，与 run、消息、歌单幂等事务放在同一关系存储，便于单机学习。代价是手动维护序列化、步骤版本和下一节点映射，不是框架自动恢复。内置 checkpointer 也不会自动解决业务幂等或第三方调用去重。

后台 Job 是单线程执行器加 SQLite 任务记录，不是分布式队列。后续有多实例、吞吐或运维需求时才引入独立队列和共享存储，并重新验证领取/重试语义；这些属于方案，不是当前能力。

### “长对话怎么处理？和长期记忆有何区别？”

持久消息在 SQLite，活动历史在带 TTL 的内存缓存；估算预算到 80% 时压缩旧消息、保留最近六条，失败裁旧。摘要是事实背景而非 system 指令。没有用户长期偏好学习，也没有精确 token 计量和摘要绝对保真保证。

看 memory.py 与 agent.py 的 _compact_context；测试 TTL、会话隔离、阈值和摘要失败降级。checkpoint 是执行状态，不要把它当长期记忆。

### “prompt injection、隐私和租户隔离如何保障？”

模型命令不能指定项目，业务按服务端范围查询，落库再校验；发送回答证据时剔除音乐对象的本地 path，prompt 把输入标为不可信。但这不是完整攻击防护：历史文本仍可能带敏感信息，默认云端要接收特征/描述/对话证据，tracing 也可能出站。

看 strict command、MusicMatch.context、范围和写入检查的测试。当前没有用户身份鉴权，项目隔离不是多租户授权，CORS 不是登录系统，不适合直接公网开放。

### “你的指标证明了什么？100% 可信度怎么来的？”

先说明版本、时间、数据、分母和指标。[历史七轮报告](quality-eval-7-rounds.md)记录 2026-09-12 的 78 首有效向量、175 次意图判定，意图准确率 84%；工具成功、自检索 Hit@3 和证据字段一致性在该样本上为 100%。这不是当前版本新验收，更不是任意用户 query 或最终回答 100% 正确。

原描述找回自身是索引闭环，逐字段一致是结构化证据检查。开放查询相关性、生成回答幻觉、真实混音体验、并发延迟与成本需独立评测；重复七轮同一意图样本也不等于独立样本扩展。没测过的指标不写进简历。

## 5. 一天的学习安排与验收

| 阶段 | 动手内容 | 不看文档也应能说明 |
| --- | --- | --- |
| 第一段：跑通 | 按教程确认前后端、分析/描述/向量三阶段；记录失败信息 | 健康检查为何不是模型验收 |
| 第二段：读主链 | 跟一次搜索，再跟一次 Set；画出自己理解的状态变化 | 自然语言如何变成参数，模型和代码如何分工 |
| 第三段：读失败 | 跑缺参考歌、约束冲突、并发和恢复测试 | 有限修复、幂等、checkpoint、fencing 的区别 |
| 第四段：模拟追问 | 90 秒介绍 + 五分钟演示；每个回答指出函数与测试 | 不靠术语包装，能说出一项限制和改进理由 |

建议做三个不改变产品范围的小练习：

- 将合成曲库的目标时长改到不可满足，先预测 validator 的结果再运行。
- 在测试中改变 query/过滤条件，预测哪些歌曲应进入候选、哪些才可向量排序。
- 找到一次 checkpoint 恢复测试，说明崩溃前已经发生的副作用与重试可能重复的计算。

最后录一段讲解，检查有没有混用“本地=离线”“checkpoint=exactly-once”“三个工具=三个子图”“通过单测=推荐质量已证明”。能避免这些概念混淆，比罗列更多组件更有说服力。

## 6. 改进建议要分清已实现与待办

当前已实现 P0 1–3 的显式执行、Set 校验/有限修复、持久步骤与幂等恢复；以相关代码和测试为依据。[P0 清单](p0%20lists.md)保留历史问题和后续计划，不把待办自动当成已完成。

如果被问下一步，优先选一个具体、可验证的问题：前端接 run_id 重试；独立音乐相关性数据集；手动调序后复核；鉴权和资源授权。说明它改善哪种失败、需要哪些测试和代价。不要承诺本轮文档中没有实现的多 Agent、分布式执行、偏好学习或公网安全能力。
