# 用 DropIt 讲清一个 AI 应用项目

重点不是把确定性代码包装成多个 Agent，而是说明语言模型、音乐模型、规则系统和数据边界各自负责什么。

## 90 秒介绍

> DropIt 是一个本地曲库分析、检索和 DJ Set 编排助手。歌曲导入后，后台用 librosa 提取 BPM、
> 调性、Camelot、能量和频谱特征，用 DeepSeek-V4.1-Flash 生成可观察的歌曲描述，再用 DashScope `qwen3.7-text-embedding` 编成向量，并将属性、描述、向量和任务状态
> 持久化在 SQLite。对话层只有一个直接编译的 LangGraph StateGraph，模型只提取 typed command 和生成最终回答，
> 确定性节点负责查曲库、找相似、排 Set。用户查询与歌曲描述用同一文本向量空间检索；标题、艺人、BPM 等走精确过滤；最终排 Set
> 由确定性规划器完成并保存。前端通过稳定 SSE 事件看到 token、工具状态和结果。系统没有普通文本
> 向量库、外部曲库搜索或伪多 Agent 流程，缺少模型和索引时明确失败。

## 演示顺序

1. 创建项目、绑定来源并导入歌曲，指出 API 先返回 202 Job，长任务不阻塞请求。
2. 展示 `analysis_status` 与 `embedding_status` 分离，以及 BPM、Camelot、energy 的真实含义。
3. 用属性条件查询曲库，再用声音描述进行歌曲文本 RAG。
4. 从明确参考歌找三首相似歌，说明 0.8 描述余弦 + 0.2 DJ 属性的重排逻辑。
5. 生成 Set，打开规则报告，展示调序、确认和导出。
6. 最后主动说明单用户、线性检索、单 worker、启发式规划和旧前端联调状态。

展示代码时按 `agent/intent → agent/graph/state/commands → agent/tools → repositories/music → worker` 讲：硬路由和 typed command 先固定任务，图节点直接执行三项业务，repository 限制数据访问，music 适配模型，worker 承担长任务。`memory.py` 提供可压缩短期上下文。

## 高频问题

### 为什么这是 Agent，不是固定 if/else？

对话先由 `IntentRecognizer` 做硬路由，再进入一次编译的 `StateGraph`。搜索、相似和 Set 的节点顺序由条件边固定，模型只做 route-specific typed command 提取和最终自然语言表达；后台分析不是 Agent 工具，因为上传后确定执行，不需要语言模型决策。这样仍是 Agent 应用，但执行过程可测试、可追踪且有明确终止条件。

### 为什么改用 librosa + 文本描述 API？

librosa 跨平台、依赖轻，提供 DJ 规则需要的 BPM、调性、节拍、响度与频谱特征。DeepSeek 把这些测量值
整理成可检查的文本，再用 DashScope 检索，描述与查询可以保持同一多语言向量空间。代价是只能表达已测量特征，不能假装识别了真实流派、歌词或乐器。

### 这算 RAG 吗？

是音乐 RAG：每首歌的生成描述是检索文档，描述向量和数据库事实保存在本地。模型必须通过 Tool 取回歌曲证据，
再生成答案；查询文本只临时编码。

### 如何避免编造和跨项目访问？

不能只说 Prompt。模型不能传 `project_id`，Tool 在服务端闭包中绑定作用域，查询再次按项目关系过滤；
Set 只能使用数据库候选或此前 Tool 返回且仍属于项目的 ID。Prompt 是行为引导，schema 与数据库查询才是执行边界。

### 为什么相似分数不是百分比？

余弦值和加权分数只在当前候选与当前模型版本下用于排序，没有经过人工标签校准。要宣称推荐质量，
需要建立带正负样本的曲库评测，测 Recall@K、NDCG 或人工偏好胜率。

### 为什么 Set 不完全交给模型？

时长、BPM、重复和曲目存在性要可复现、可测试。规则规划器负责这些约束，模型负责理解模糊要求和
解释结果。当前规划器是贪心启发式，不能声称全局最优，也没有独立 Critic Agent 自动重试。

### 用户的歌曲是否完全不出本机？

librosa、歌曲描述模型与文本 embedding 模型都在本地运行，不上传完整音频到音乐分析云。但聊天模型会收到用户消息与 Tool 返回的
曲目元数据；启用 LangSmith tracing 后还会发送 tracing 数据。部署时必须给用户准确的数据说明。

### 当前能否商用多用户？

不能直接这样说。当前是单用户本地服务，没有登录、租户字段、访问令牌或对象级授权。项目范围只能
限制 Agent 当前查看的曲库，无法隔离不同用户。商用前需增加租户身份、所有查询的 owner 条件、
独立或带租户键的数据/文件空间、配额、审计与删除流程。

## 可以诚实提出的改进

- 用真实 DJ 曲库建立文本查询与相似歌评测，而不是只跑接口 smoke test。
- 大曲库改用带模型版本和租户过滤的近似向量索引；当前 NumPy 全量余弦是线性的。
- 把分析任务迁移到独立持久化 worker，增加取消、限流、资源配额和可观测性。
- 将 Set 规划升级为束搜索、动态规划或约束求解，并把混音重叠纳入时长模型。
- 在接入用户前完成认证、曲库隔离、隐私披露和模型权重许可证核查。

不要说“Cyanite 外部搜索”“三个 Subagent 协商”或“模型自动识别完整流派标签”，
这些都不是当前实现。当前确实使用 Chroma 保存音乐向量。具体参数见[接口参考](reference-api-tools-and-data.md)，运行边界见[教程](tutorial-run-and-observe.md)。
